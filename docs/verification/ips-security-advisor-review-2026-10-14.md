## Concrete finding and focused test gaps

**Charge-account wrapper performs existence-sensitive work before authorization.** In [`20260930102000_preserve_charge_account_label.sql`](../../supabase/migrations/20260930102000_preserve_charge_account_label.sql#L24), `create_manual_tenant_charge_with_account` first reads the supplied organization's lease, then checks account compatibility and idempotency bindings, and only later calls the authorized charge command. The rollback-only local reproduction confirmed that an authenticated outsider who knows an organization/lease UUID pair can distinguish an existing lease plus nonexistent account (`22023`, `finance_lease_charge_account_incompatible`) from a nonexistent lease (`42501`, `Not authorized`). The later command checks `auth.uid()` and organization-admin or property-scoped `finance.record_payments` permission before charge creation. No successful unauthorized financial mutation has been demonstrated. The reported defect is the earlier error oracle; guessing a UUID without prior knowledge is not a practical enumeration claim.

The release lead authorized and an independent reviewer approved a narrow guard-order repair preserving that existing effective permission. [Migration 20261014140000](../../supabase/migrations/20261014140000_manual_charge_authorization_first.sql) adds the same permission check before lease/account/binding reads, retaining downstream checks and behavior. It was applied only to the verified isolated database with normal pinned Supabase CLI `migration up --local`; the ledger advanced from 211 to 212. No existing migration was edited and no hosted write occurred.

The [rollback-only regression](../../supabase/tests/manual_charge_authorization_first_test.sql) executed 13 assertions. Before the fix, four expected denials instead reached account validation: foreign-organization administrator, wrong-branch writer, same-branch viewer without payment permission, and missing authenticated user. The missing foreign lease returned 42501, demonstrating the differential. After the fix, **13/13 passed**. Both allowed actor classes (organization administrator and same-branch payment writer) reached the same ordinary account validation before and after. Invoice-line, activity, and binding counts were unchanged on rejected calls. An initial fixture setup attempt needed an explicit enum cast; that transaction rolled back before the successful pre-fix reproduction.

A bounded postflight verified 212 migration ledger rows, the applied function body exactly matching the new migration, and the former body unchanged after the added guard. Effective grants remain `anon=false`, `authenticated=true`, `service_role=true`; definer mode and empty search path are unchanged. Artifacts: `.codex-artifacts/manual-charge-authorization-before.log`, `manual-charge-authorization-after.log`, `manual-charge-authorization-migration-up.log`, and `manual-charge-authorization-postflight.json`. The release lead owns the full 212-migration suite, type parity, lint, and recovery checks. **This fix closes the demonstrated information leak; it does not remove the intentional authenticated-definer advisor category.**

## Interpreting and reducing the warnings

The definer warning flags an exposed privilege boundary. The local catalog shows explicit authentication/authorization helpers or delegated checked commands throughout the sampled workflows, but matching a helper's name is not proof of correct order, input binding, or every branch. The charge-wrapper issue illustrates that limitation. Preserve necessary transaction APIs and review each obsolete signature before revoking execution or replacing it with an invoker wrapper. PostgreSQL definer functions run with their owner's privileges; current Supabase guidance recommends invoker by default and a fixed, qualified search path where definer is necessary.
