# Proposed synthetic daily workflow acceptance

This is test tooling only. The new browser journey has not yet run; passing policy tests is not a browser acceptance result. Publication and execution require the coordinator's approval. No product, database migration, financial permission or staff assignment changes are included.

## Workflow and source

`.github/workflows/daily-workflow-acceptance.yml` is a new, dedicated PR-only workflow using the repository's existing GitHub-hosted `ubuntu-latest` infrastructure. The existing `.github/workflows/ci.yml` and protected checks are unchanged. It runs for a same-repository PR touching the new workflow/harness files and checks out the exact PR head, with credentials not persisted.

Branch scope: `test/daily-workflow-ci-20261005`, based on production main `164b2cf93a4974bed2ae2fe5b030263dc0efc953`. The branch contains only this document, the new workflow, `scripts/daily-workflow-policy.mjs`, its focused node tests, `scripts/run-daily-workflow-ci.mjs` and `scripts/smoke-daily-workflow.mjs`. Keep diagnostics, deposits, role-design work and PR223 dependencies separate.

## Exact job

1. Install the existing lockfile, run the 35 boundary/completion tests, and install its pinned Playwright Chromium/browser dependencies.
2. Require the exact repository, PR event, Linux runner, run ID/attempt and checkout SHA. Refuse hosted Supabase/Sentry credentials, dotenv files and existing containers/volumes/network matching this run's unique project.
3. Start a disposable project `nestory-daily-<run-id>-<attempt>` with DB, auth, PostgREST, gateway and storage only. Exclude analytics, realtime, Studio, mail, metadata and edge runtime. Before fixtures, bind the new DB/API explicitly to localhost and verify ownership/ports. All migrations apply only to this new runner database.
4. Load the existing synthetic baseline once, then execute only `historical_rent_correction_authority_test.sql` and `historical_rent_correction_execution_test.sql` for the scoped authorization, correction, closure, replay and stale protections. There is no full SQL-suite rerun inside this new job.
5. Read local keys into process memory, mask them, stop this job's services during one `next build --webpack`, and use the exact local API configuration. Restart the same services and use `next start`, avoiding development compilation during browser work. Verify the app's local-target attestation before login.
6. Run one browser serially: create and confirm a zero-deposit synthetic lease; issue rent through the UI if required; record a 40 payment on a 120 invoice; preview/save the current month at 100 with a reason and 60 balance; verify original payments, future terms and invoice evidence; redownload and hash-check the unchanged receipt; close/publish and hash-check the corresponding owner statement. Check Finance Member UI denial. No fixture reset occurs between these phases.
7. The owner allocation, period generation, month lock and pending synthetic opening resolution use existing checked authenticated commands from the established rent-browser acceptance helper. Closing and publishing the statement remain visible UI actions. This is explicitly mixed UI plus checked accounting preparation, not a claim that every preparatory action is clicked through the browser.
8. Require all five phases in order for completion. Preserve only sanitized logs, synthetic screenshots and pass/failure metadata. Always remove only this job's containers/volumes/network and restore config. A failed step is not bypassed with a direct financial write.

The fixture already grants lease preparation/activation to Finance Manager; Operations Manager does not hold those permissions in this baseline. The journey uses the existing Finance Manager and Super Admin actors without altering memberships or grants. It does not resolve the separate A/B permissions-design gap or demonstrate every property/role combination. The existing focused SQL tests supply the relevant rent-correction boundaries; broader policy decisions remain separate.

## Access, network and cost

- Only `contents: read` repository permission; no `pull_request_target`, push trigger, protected environment, deployment permission, hosted credentials, linked project, new account or persistent credential. Synthetic local runtime keys are generated by the existing CLI and discarded with the runner.
- Standard existing runner network access is needed for npm, pinned GitHub actions/container images, Playwright downloads and Ubuntu browser dependencies. The browser itself permits only the attested localhost app/API. No production customer data is fetched or written.
- One job, no matrix, 30-minute hard timeout, no automatic retry, cancellation of superseded PR runs, three-day allowlisted evidence retention. A 4 GiB initial/build memory threshold and 768 MiB/8 GiB stop floors remain. Child process groups are stopped on resource/deadline failure.
- The additional job has a maximum 30 runner-minutes per attempt. Opening/updating the PR also triggers the normal existing protected CI, whose cost is additional; it is not skipped or weakened. No purchases or paid runner class are requested. Neither remaining Actions allowance nor live Codex reserve was verified here; obtain the bounded-run decision before publication.

## Local evidence and remaining decision

The first local acceptance attempt replayed 192 migrations and loaded fixtures, but stopped before login at 0.624 GiB free memory. After the deposit worker released its slot and the verified idle task-7 controller was stopped, only about 3.34 GiB remained; the 4 GiB admission guard refused the retry. No new end-to-end pass or app defect was established.

The 35 new policy tests, script syntax and lint checks passed. The workflow YAML parsed successfully with the existing `js-yaml` dependency; its PR-only trigger, single job, eight steps, read-only permission and timeout were checked. All action references are pinned to full commit SHAs. The repository secret scan passed across 1,837 tracked files, including the staged new files, and the staged diff whitespace check passed. These are local tooling checks only. A first cloud run is still needed to validate browser selectors, synthetic setup and the continuous financial journey. Any failure must be classified as an application defect versus a harness/fixture issue before changing product behavior. No release follows automatically from this workflow.
