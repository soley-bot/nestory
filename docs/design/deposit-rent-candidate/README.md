# Preserved deposit SQL candidate

These five files are review inputs, not installed migrations. Their SHA-256
digests in `manifest.json` pin the SQL recovered from the earlier deposit work.
The historical comments and filenames are preserved verbatim, including old
"UNEXECUTED" notices; current execution evidence belongs to the new run below.

The report-reader companion already defines
`get_local_lease_deposit_report_snapshot`. Do not also install the identical
historical `deposit-rent-local-source.sql` draft.

Run `node scripts/test-deposit-candidate-local.mjs` from the repository root on
the verified local Docker engine. It creates its own uniquely named database,
copies the local main database's schema only, applies later repository migrations
and these pinned companions, and loads only fictional fixtures. It generates new
synthetic runtime capability values without reading source capability rows.
Temporary test grants apply only in that generated database. The source database
and hosted projects receive no writes. The generated database is dropped in
`finally`; `artifacts/deposit-candidate/run.json` records completion and cleanup.

This harness proves compilation against the current local schema and selected
real permission/financial behavior. It is not a fresh migration-chain reset,
Supabase Auth/session test, browser test, hosted acceptance or release approval.
The fixture command setup uses a privileged local connection; the tested journal,
receipt and reader boundaries explicitly switch to the ordinary `authenticated`
role with synthetic actor identities. Direct application/reversal setup calls
are identified separately in the evidence and are not API grant proof.

Promotion requires the complete access assessment, approved forward migration
identities generated by the installed CLI, fresh database/type checks and actual
authenticated acceptance on the final assembled candidate. See
`../../runbooks/deposit-release-access-assessment.md`.
