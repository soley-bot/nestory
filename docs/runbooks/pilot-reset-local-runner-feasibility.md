# Existing Docker Desktop runner assessment

Read-only assessment, 27 October 2026. **The existing Docker Desktop engine is not a provision-ready protected executor.** Linux capability and encrypted host storage are available, but the current mount, runner identity, workflow isolation and private-access requirements are not jointly satisfied. No runner, account, volume, key, grant or customer archive was created for this assessment. The unconditional hosted mutation hold remains unchanged.

The owner subsequently selected preparation of the [GitHub-hosted route](pilot-reset-github-hosted-execution.md), which uses independent external recovery storage. This local-host assessment remains evidence for that decision; it is not a request to encrypt D: or register the shared Docker host.

## Observed constraints

| Requirement | Evidence and consequence |
| --- | --- |
| Linux with Node 24 | The existing local engine is Linux x86-64. A dedicated runner image with Node 24 and the pinned PostgreSQL client still needs construction and verification. Linux runtime tests do not establish protected provisioning. |
| Dedicated persistent filesystem | `assertPersistentMount` requires exactly one mount at `/var/lib/nestory-reset`, filesystem root `/`, a pinned source hash and ext4/xfs/btrfs. An existing Docker named volume was inspected without changing it: its ext4 mount root is `/data/docker/volumes/<volume>/_data`, so the ordinary named-volume pattern fails this guard. A new named volume alone would not solve this. |
| Stable enrolled runner identity | Configuration, provisioning and live job verification pin the numeric GitHub runner ID. The workflow performs one action per job. A GitHub `--ephemeral` runner deregisters after one job; each new registration requires a fresh identity and corresponding reviewed bindings. A disposable container reused across phase jobs is not the same lifecycle as a GitHub ephemeral runner. [GitHub runner lifecycle](https://docs.github.com/en/actions/reference/runners/self-hosted-runners). |
| Enforced workflow isolation | Read-only GitHub metadata reports a personal-account public repository and no repository runners. Organization runner groups can restrict selected repositories and workflows, but that facility does not attach an organization runner group to this personal repository as-is. A routing label is insufficient: a different job reaching the runner could execute before this program's identity checks and access mounted private files. The protected environment and writer concurrency apply to this workflow, not every possible job. [GitHub runner access policies](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access). |
| Private access across the whole storage chain | Host inspection found the worktree, temporary directory and Docker VHD on the encrypted system drive. It also found read/execute access for the sandbox group on the VHD and ordinary artifact directory. This does not prove private access. POSIX permissions inside the VHD cannot remove Windows access to its backing file; full-drive encryption does not remove access granted to a signed-in principal. Docker documents the host/WSL access boundary. [Docker WSL security](https://docs.docker.com/desktop/features/wsl/). |
| Capacity and recovery | Approximately 11 GB of system-drive free space was reported during assessment. Capacity for images, encrypted archives, restore working space, logs and retained evidence is unproven. Linux virtual free space is not sufficient evidence of host capacity. No customer archive size was measured or copied. [Microsoft WSL disk guidance](https://learn.microsoft.com/en-us/windows/wsl/disk-space). |

## Bounded provisioning decision

Do not register a runner on the shared engine or create a named volume as the next step. Both would leave material requirements unresolved. A private Windows artifact folder alone would also leave the shared Docker backing store and runner scheduling boundary unresolved. Changing the shared Docker VHD ACL is a wider host change and is not proposed here.

For the implemented POSIX route, a concrete provisioning review must first select an execution context with enforceable workflow access and separately private backing storage. This requires either an explicitly reviewed repository/account arrangement supporting the required runner policy, or a separately implemented equivalent dispatch boundary. Neither is present in this assessment, and no purchase or repository transfer is assumed.

Once that context exists, the smallest compatible host plan is one dedicated non-root runner account, a separately mounted filesystem rooted at `/var/lib/nestory-reset`, private `/etc/nestory-reset` configuration/client CA/passfile, and one stable enrolled runner identity for the operation, retired afterward. If one-job ephemeral registrations are required, review and implement the lifecycle/rebinding design first. Do not silently reuse old provisioning hashes or relax the mount check to accept an arbitrary subdirectory.

Before enrollment, verify the actual host and container access chain, measured capacity, pinned binaries and CA, cross-job journal durability, encrypted archive readback, key recovery and independently usable restore evidence. Provisioning documents must bind the observed runner identity, filesystem source and store IDs. Existing synthetic database/HTTP and Linux filesystem tests establish only their tested behavior; they do not supply these operational proofs or claim that a customer reset occurred.
