# Synthetic recovery rehearsal

Run `npm run recovery:test-synthetic` for serial mocked safety checks. Run `npm run recovery:rehearse-synthetic` only when local Docker access and temporary synthetic resources are authorized. The command accepts no backup path, database URL, credentials or target arguments. It never reads customer backups or invokes Nestory runners.

Before any daemon operation, the CLI rejects Docker environment target/configuration overrides and resolves the active context's endpoint through local CLI metadata. Only the Windows local `docker_engine`/`dockerDesktopLinuxEngine` named pipes or Linux `/var/run/docker.sock` are supported. Remote TCP/SSH, TCP loopback, unknown sockets/pipes and overrides fail closed; do not alter access or unset variables to bypass a rejection. Every daemon operation, including cleanup, pins the verified endpoint with `--host` and a fixed environment snapshot. The workspace disk check measures local host space, not the Docker VM's free disk.

The rehearsal inspects the cached `postgres:16-bookworm` image, requires a valid image ID and digest, then runs the immutable inspected image ID with `--pull never`. A unique labelled container has no network, published ports or host mounts. PostgreSQL data is tmpfs (256 MiB); scratch is tmpfs (16 MiB); memory is capped at 512 MiB, CPU at one and processes at 128. Local socket trust is confined to that disconnected disposable container. No persistent credential or shared security setting changes. Existing Supabase/Moodle containers are untouched.

At least 8 GiB free on the workspace drive is required. Space is checked before creation, before dumping and before file-archive work. Falling below the floor stops the rehearsal and triggers cleanup. Each CLI subprocess has at most a 15-second timeout and 1 MiB output limit. Work uses a monotonic 60-second deadline; subprocess timeouts and disk checks are capped to the remaining budget. Final PostgreSQL readiness probes loopback TCP (`127.0.0.1`), which excludes the initialization server's socket-only phase. Readiness has a 30-second deadline within the work budget, with no arbitrary attempt cap; a late readiness success is rejected. SQL is not retried. Cleanup has a separate 30-second deadline, so the work/cleanup span may approach 90 seconds. CLI/context/disk preflight and final disk observation are separate bounded subprocesses, not included in the core work timing. No dependency/image installation, hosted resource or paid service is created.

The command creates two fictional tables in a new synthetic source database. A custom-format `pg_dump` is restored into a separate fresh database with `pg_restore --exit-on-error`. Validation checks row counts, matching account/entry totals, an index, RLS flag/policy metadata, and rejection of invalid foreign-key/negative-balance inserts. A separate synthetic file tar archive is restored, compared byte-for-byte and hashed. Success requires actual validation markers and matching file hashes; a successful restore process exit alone is insufficient.

JSON evidence includes local endpoint, exact container name, immutable image ID/digest, dump byte size/hash, file hash, elapsed/recovery timing, free space and cleanup confirmation. Preserve that JSON in the approved evidence location. Dump hashes can vary between runs; compare against the evidence for that run. Cleanup checks the exact random container name and synthetic label before removal, including after an uncertain create result. A failure exits nonzero with sanitized JSON containing the name, pinned endpoint, original work phase/error and any cleanup phase/error; cleanup errors cannot replace the work error. No subprocess stderr, SQL or credential values are logged. `removed=false` means cleanup is unconfirmed, not a guarantee the container still exists. Inspect only that exact name at that same endpoint and recheck its synthetic label before any manual removal; do not delete shared containers or broaden removal to a prefix/label set.

This is **mechanism verification**, not production recovery proof. PostgreSQL16 differs from hosted Supabase17; fixtures do not exercise Nestory schema/migrations, production data, effective Auth/RLS access, Storage API/object backups, hosted physical/PITR checkpoints or service startup. The file roundtrip verifies bytes separately from database metadata, but never establishes real Storage coverage. Tiny fixture timing is not a production RTO estimate. The command creates no schedule and does not alter retries or telemetry.

For actual recovery, obtain the current checkpoint inventory, completion/retention/PITR window, source identity, independently retained backup integrity evidence, separate Storage-byte catalog, recovery owner and approved RPO/RTO. A representative customer-data or hosted restore requires its own reviewed scope and approval. Never restore/reset a shared or production database to verify a backup. Keep historical exports distinct from the current hosted backup inventory.
